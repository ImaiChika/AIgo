# AIgo 工业化使用差距分析

> 更新：2026-09-02。本文以《功能需求文档.txt》为基准，结合代码审阅及管理员、审题专家两类用户的本地端到端体验整理。

## 一、结论

当前系统已具备内部试用和小规模客户试点能力：知识点管理、AI 出题、题库管理、权限菜单、多轮审核、基础审计、容器部署、逻辑备份恢复和客户端加密异机备份均可运行。但正式生产交付仍缺客户真实对象存储的 WORM 验收、监控告警、镜像发布和本地模型生产验收等工程能力，当前成熟度约为 **7/10**。

最优先的差距不是“页面还不够多”，而是审核结果是否可信、题目是否能被可靠追溯，以及服务故障或并发时是否会产生错误状态。只有这些基础成立，后续的 AI 能力和界面优化才有价值。

## 二、本轮核验结果

- 使用独立空数据库完成初始化，CLI 导入 589 道题，网页导入 7235 个知识点；重复导入验证了题目覆盖和知识点去重，不接触现有业务库。
- 以管理员、两轮审题人、最终把关人、受限题库用户、自注册无权限用户等账号，完整走通题库配置、角色与账号、权限矩阵、知识点、题目 CRUD、审核流程配置、送审、逐轮投票、退修重提、驳回、撤销、最终入库、结果统计、审计和 xlsx/docx 导出下载。
- 验证了显式审核人、按题库范围自动匹配、通过票数门槛、一票否决三类流程；越权访问、禁用账号、未认证下载、跨题库访问、非法 JSON、超大请求体、CORS、路径穿越和异常搜索均按预期被拒绝或安全处理。
- 20 轮并发双人投票、20 轮并发重复送审及双后端实例交叉写入均通过；300 个并发读取请求无错误，中位响应约 104ms，P95 约 1.89s。
- `go build ./...`、`go vet ./...`、`go test ./...`、审核包竞态测试和前端 `npm run build` 均作为本轮回归门槛。
- 按测试边界未调用真实千问或 AI 检查服务；批量任务仅检查页面和历史列表，没有提交外部任务。

### 已完成的基础加固

- 服务拒绝使用默认 JWT 密钥启动；空库管理员密码不再固定。
- 题目、审核和导出接口已做题库范围校验。
- 请求体已限制为 10MB，CORS 改为白名单，HTTP 服务已有超时和优雅关闭。
- 题目创建、编辑、AI 生成、提交审核、最终通过和发布共用同一套格式校验；不合格题只允许保留为待修复草稿，不能进入正式题库。
- 全新数据库可一次完成建表；默认审核流程不再绑定本地演示账号，改为按审题权限和题库范围匹配审核人。
- 送审、投票、最终决断、流程变更和撤销使用 PostgreSQL 跨进程锁串行化；双实例并发测试中不再出现丢票或同题重复任务。
- 送审、投票、最终决断、退修重提、撤销和发布的审核记录、任务与题目状态已纳入同一 PostgreSQL 事务；六类中途失败故障注入、真实 PostgreSQL 回滚和双连接池并发测试均通过。
- 题目已建立不可变内容快照；新建、编辑、Excel 更新和历史恢复统一生成版本，状态/题库变化不虚增版本。审核任务绑定提交时版本，投票和决断会拒绝版本不一致；并发编辑只有一个能生成下一版本。
- 版本迁移兼容早期 `question_versions(id/snapshot TEXT/changed_by)` 表结构；已用完整业务库副本验证 5260 道题和 415 个审核任务无损回填。`start.sh` 现在会等待后端真实就绪，迁移失败时打印日志并退出，不再只启动前端后虚报成功。
- 审核中和待决断题目禁止静默编辑，必须先撤销提交或由把关人退回修改；草稿、退修题仍可按原流程编辑。
- Excel/Word 只允许导出 `published/已通过` 题目，草稿、审核中、退修和驳回题无法绕过状态直接导出。
- 题库页已改为页码分页，跨页勾选不会丢失；“全选全部筛选结果”会把题库、专业、状态和关键词筛选传到后端，Excel/Word 使用同一范围。导出文件已补齐有效工作表范围、唯一文件名和审计日志。
- 题库和 AI 检查的左侧工作区已拆分为固定工具栏与独立纵向列表，搜索、筛选、全选和导出/检查按钮不再随题目滚动；题库卡片使用独立固定操作列，长摘要不会再遮挡状态和删除按钮。常用桌面宽度下已消除内容区横向拖拽，题库右侧详情布局保持不变。
- 题库、知识点主表、知识点选择器和题库管理的搜索结果均已将分页从长列表中剥离：列表单独滚动，页码固定在容器底部，翻页后自动回到新一页顶部。
- 已增加公开且脱敏的 `/health/live` 与 `/health/ready`：存活检查不访问依赖，就绪检查在 2 秒内验证 PostgreSQL 和关键业务 Schema；LLM 和批量云服务不作为题库浏览/人工审核的启动阻断条件。`start.sh` 已改用 readiness 判断后端真正就绪。
- 已建立正式版本化数据库迁移：`schema_migrations` 记录版本、名称、SHA-256 校验和和应用时间；`aigo migrate` 独立执行，单个版本在事务中失败即回滚，并用 PostgreSQL advisory lock 防止多进程重复升级。其他命令只做版本检查，未迁移、迁移记录断档、程序版本过旧或历史迁移被篡改时均拒绝运行；`start.sh` 会先迁移再启动服务。
- 版本化迁移已通过空库并发初始化、重复执行、故障注入回滚、迁移记录篡改、运行中版本漂移及完整业务库副本升级测试。实际本地库升级前已备份，5260 道题、415 个审核任务和 5260 个版本快照的逐行内容哈希在升级前后保持一致。
- 已建立正式构建与单进程运行入口：`build-production.sh` 按 lockfile 构建 Vue 静态资源和 Go 二进制，生成不可变的版本化 release，并通过 `output/production` 切换当前版本；`run-production.sh` 前台运行、先迁移数据库，再由同一 Go 进程托管 API 与前端，不依赖 Node/Vite，也不负责启动或停止外部 PostgreSQL。
- 正式静态托管支持 Vue history 深层刷新，API/健康检查不会被 SPA 回退覆盖；缺失资源和隐藏文件返回 404，带哈希资源使用长期不可变缓存，HTML 禁止强缓存。生产运行不读取项目 `.env`，支持通过进程环境/Secrets 或显式的外部 `AIGO_ENV_FILE` 注入配置。
- 正式运行已用真实浏览器完成管理员登录、题库和审核结果深层链接及刷新测试，页面、控制台和 HTTP 错误均为 0；运行中构建新 release 时旧进程继续使用旧物理目录，重启后才加载新版本，避免新旧首页和资源混用。
- 已增加单机构 Docker Compose 部署骨架：多阶段应用镜像最终约 9.6MB，以 UID/GID 10001 非 root 运行，根文件系统只读；PostgreSQL、应用输出和 Caddy 证书使用独立持久卷，应用 8080 与数据库 5432 不发布到宿主机。基础镜像按已验收 digest 固定，升级需显式变更。
- PostgreSQL healthy 后先运行一次性迁移容器，迁移成功后应用启动，应用 healthy 后 Caddy 启动。数据库、JWT 和初始管理员密码通过 Compose Secrets 文件挂载，真实 Secret 内容不进入容器环境；Caddy 提供 JSON 访问日志、错误 Host 421、HTTP→HTTPS、主动 readiness 检查和安全响应头。
- 隔离容器环境已完成首次空库部署、管理员登录、题库与审核页面刷新、非敏感题库写入、数据库停机/恢复、Go 进程 SIGKILL 自动重启、整套容器 down/up、迁移幂等和数据卷持久化测试；本地 HTTPS、HTTP→HTTPS 跳转及公网域名 Caddy 配置校验均通过。未调用出题或 AI 检查服务。
- 已增加独立非 root 逻辑备份服务：部署后立即备份并按间隔循环，备份卷与数据库卷分离；custom archive、SHA-256、Schema/应用/PostgreSQL 版本和核心表稳定指纹一并保存，按保留天数和最大份数双重清理。自动、手工校验和恢复通过跨容器 `flock` 串行化。
- 恢复工具禁止覆盖当前业务数据库，只能恢复到新数据库；恢复使用 `template0`、单事务、遇错退出和 `ANALYZE`。隔离环境已通过手工备份、一个字节篡改拒绝、临时库恢复指纹比对、保留式恢复、主库覆盖拒绝、宿主机异机暂存目录导出校验，以及整套容器 down/up 后备份卷和业务数据持久化测试。
- 已增加独立可选的异机备份 Compose 扩展：服务只读本地备份卷，用 `age` 接收者公钥加密 `.dump/.sha256/.meta` 三件套，应用服务器不保存私钥；S3 凭证由独立 Secrets 注入，状态卷、资源限制和运行权限与应用隔离。未配置异机存储时主 Compose 的既有启动、迁移、本地备份和恢复不受影响。
- 异机上传采用加密包、密文 SHA-256、receipt 的提交顺序和不可覆盖写入；上传后完整回读密文计算 SHA-256。重复扫描幂等、状态卷丢失可从 receipt 恢复，同名源哈希冲突、远端篡改、空下载和错误校验文件均会拒绝；对象存储断网后有限重试并自动恢复，不会修改源备份。
- 已用真实 PostgreSQL custom archive 完成“加密上传→远端下载→离线私钥解密→三件套导入→校验→临时库恢复与核心表指纹核对”的端到端演练，并覆盖并发锁、容器重启和失败残留清理。由于本地测试 S3 不支持真实 Object Lock，客户 bucket 的版本控制、默认 WORM 保留和无删除/无绕过权限仍必须在上线环境另行验收。
- **注册产品口径已确认并实现**：自助注册默认开启，可由运维开关紧急关闭；注册用户以空角色、空直接业务权限、空题库范围创建，只保留登录和基础浏览能力。管理员在「用户管理」自动看到“新注册”账号，可分配角色模板、直接权限、题库范围及启用状态，权限变化对既有Token实时生效。
- 登录使用持久化的独立账号桶和来源IP桶：账号连续第8次失败、同IP第30次失败开始短时指数阻断，成功登录只清账号桶；同IP公开注册允许5次业务尝试，第6次开始限速。失败和限速写脱敏审计，只保存账号/IP短哈希；不存在账号执行dummy bcrypt，禁用判断位于密码比较之后，客户端统一返回通用错误。受控Caddy才注入可信客户端IP，直连默认不信任转发头。
- 已全仓检查批量/实时推理日志，不再输出API Key内容或前后片段。实际库升级前已备份，Schema 3新增限速表后题目、审核任务、版本快照和用户表逐行哈希保持不变；真实浏览器已走通注册→低权限403→管理员自动可见→分配teacher→重新登录获得题库权限。

以下清单只保留尚未解决、且值得投入的差距。

## 三、P0：当前核心数据一致性项已完成

审核跨表事务、跨实例并发保护、题目版本快照和审核版本绑定已经完成并通过真实 PostgreSQL 测试。当前非外部 LLM 调用范围内，暂未发现新的核心数据一致性阻断项；正式交付前仍需完成以下 P1 工程能力。

## 四、P1：近期应完成的生产能力

### 1. 外部调用与批量处理尚不可靠

单题 AI 出题仍是同步 HTTP 请求，缺少任务状态、取消、重试、并发限制、用户配额和成本统计。批量下载/导入也需要明确的幂等标识，避免重复操作写入重复题目。

**建议：** 先把文本出题、AI 检查和批量导入任务化；记录请求、模型、耗时、token/费用、原始响应和失败原因。

### 2. 缺少可部署、可观测、可恢复的运行方案

开发启动方式仍保留 Homebrew PostgreSQL、`nohup` 和 Vite；正式路径已经具备 Compose、独立 PostgreSQL、Caddy HTTPS、健康依赖、Secrets、持久卷、逻辑备份恢复和客户端加密异机上传。距离客户商业交付仍缺真实对象存储 WORM/凭证策略验收、应用与数据库联合回滚、镜像仓库/扫描/签名、结构化应用日志、指标告警，以及真实公网域名和客户 Linux 服务器上的部署演练。

**建议：** 在首个客户对象存储上完成 Object Lock、最小权限和失败通知验收后，下一开发步建设可重复的镜像发布与供应链基线；随后补结构化日志、基础指标和告警。

这里的“先做部署”不是立即把当前版本交付给真实用户，而是先建立可重复的生产形态：开发、测试、试点和生产环境隔离，配置与 Secrets 外置，前端使用静态构建，后端和 Worker 可独立扩缩，数据库继续使用已建立的正式迁移并补齐备份恢复流程。该基础会直接决定后续任务队列和 workflow 的运行方式。

### 3. 账号仍缺企业级身份能力

自助注册、最低权限、管理员授权、账号/IP限速和失败审计已形成明确口径。当前仍没有密码找回、MFA、企业身份认证、注册通知和集中式安全告警；这些能力是否必须取决于首批客户的身份管理要求。

**建议：** 小规模单机构试点先使用当前“自助注册+管理员授权”模式；涉及更高安全等级或统一身份平台的客户，再接入OIDC/SAML/MFA和密码恢复，不在当前阶段提前引入复杂身份平台。

### 4. 审题工作台不能承受真实待办量

当前专家一次会看到 404 项待审任务，但没有搜索、筛选、分页、优先级、截止时间、转派或批量处理能力。单题详情与投票界面可用，但大规模任务下会直接影响审核效率和遗漏风险。

**建议：** 为“待我审核”和“待决断”增加按题库、专业、状态、提交时间的筛选与分页，并补充任务转派、超时提醒和处理优先级。

### 5. 列表与汇总仍以全量内存处理

题目、审核结果和部分统计接口会先读取全部题目、任务和记录，再在 Go 内存中筛选分页。当前数据量尚能响应，但数据持续增长后会拖慢页面并增加数据库和服务内存压力。

**建议：** 将常用筛选、聚合和分页下推到 PostgreSQL，并为审核任务、状态、题库成员关系和创建时间建立相应索引。

### 6. 本地 Qwen 目前只有接口预留，尚不是生产能力

实时推理已经支持 `QWEN_DEPLOYMENT=local` 和 OpenAI-compatible 地址，但项目尚未提供本地模型服务本身，也没有 GPU 调度、模型预热、健康检查、容量规划、并发背压、故障切换和升级回滚方案。未来计划使用本地部署的 Qwen 3.5 模型时，还需要验证医学 A2 命题质量是否达到或超过当前基线。

**建议：** 将本地模型服务视为独立生产依赖。固定实际 served-model-name 和模型版本，分别记录云端 `qwen3.5-flash` 与本地模型的运行数据；完成离线质量评测、单请求和并发压测、显存与吞吐测量、超时/重启/不可用演练后，才能把默认实时推理切换到本地。不要因为 OpenAI-compatible 接口已预留，就在产品状态中宣称本地模型已经可用。

### 7. 多用户交付边界需要先固定

现有 RBAC、题库范围和审核人配置已经支持一个机构内部的多用户协作，但数据库没有完整的机构/租户隔离模型。真实多用户部署如果指“同一客户机构内多角色使用”，可以沿用当前结构；如果指“多个客户机构共享同一套服务和数据库”，则需要新增全链路 tenant 隔离，并重新审查唯一约束、查询过滤、审计、备份恢复、模型配额和管理员权限。

**建议：** 第一版生产交付采用“单机构单部署、机构内多用户”，先把可靠部署和客户试点做好。多租户 SaaS 仅在商业和产品需求明确后另立项目，不把它混入当前生产化整改。

## 五、P2：在核心稳定后补齐

- 知识点导入批次记录和回滚能力。
- 面向医学命题的固定质量基准集、重复题检测和模型/prompt 回归测试；AI 继续定位为辅助工具，正式入库必须经人工审核。
- 审计日志的完整性：重要操作记录前后差异；正式题库的删除、导出与回滚策略明确化。
- 演示数据、测试数据和客户生产数据分离。当前库中保留大量测试题与 404 项待审任务，不应直接交付给客户使用。

## 六、建议实施顺序

1. **继续搭建生产运行底座（P1）**：数据库迁移、健康检查、正式构建、Compose、Secrets、持久卷、Caddy HTTPS、逻辑备份恢复、客户端加密异机上传及账号入口加固已完成；下一步完成真实 bucket 的 WORM/最小权限验收、镜像发布与扫描、应用+数据库回滚边界、结构化日志、指标和告警。此阶段仍不直接开放正式客户流量。
2. **建设多用户与最小持久任务能力（P1）**：补用户配额和任务归属；将文本出题、AI 检查、批量导入任务化，补齐幂等、取消、有限重试、并发限制、背压、重启恢复和完整运行记录。
3. **接入并验收本地 Qwen 3.5（P1）**：在上述部署和任务底座上接入实际本地模型服务，完成质量基准、容量压测和故障演练，再决定是否替换当前云端实时链路。
4. **实现受控 Agentic Workflow（P2）**：只实现固定状态图中的“生成→规则校验→AI 复核→最多 1-2 次定向修改→人工审核”，不让模型自由选择发布、绕过审核或无限循环。
5. **小规模真实用户试点（P2）**：通过生成成功率、专家退回率、平均审核时间、单题调用次数、P95 延迟和失败恢复率判断 workflow 是否真正有收益。
6. **产品完善（P2）**：继续完善数据治理和审计。

## 七、最终判断

当前版本适合：内部流程演示、小规模专家试用、审核规则验证和 AI 生成质量实验。

核心审核一致性、部署骨架、逻辑备份恢复、客户端加密异机上传和账号入口基线已经具备小规模客户试点条件；在真实存储 WORM 验收、监控告警、镜像发布、持久任务、本地模型生产验收和数据查询扩展性完成前，仍不建议作为无人值守的正式生产系统交付。

当前应当**先做真实环境部署的开发基础，同时把单步 AI 调用抽象成持久任务；暂不先做完整 workflow**。生产底座和任务层稳定后，再实现受控的生成—复核—修改循环。否则 workflow 只会把多个同步、不可恢复的调用连接成更长的故障链。

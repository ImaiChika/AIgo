## 1. 项目一句话定位

面向国家执业医师考试 **A2 型试题**的 AI 辅助命题系统：
知识点 Excel / CSV / Word 表格 → 千问生成题目草稿 → 首次 AI 质量检查（自动异步）→ 多轮人工审核（可配置）→ 最终把关通过，支持 xlsx/docx 导出。

当前题型统一为纯文本 A2 单选题。AI 生图、题目图片、多模态素材和图片审核已经永久退出当前项目范围；Web 批量推理使用本地单题 API 队列，CLI 仅保留历史 DashScope 兼容路径。

- **新题修改与提交审核**：命题教师在「新题修改与提交审核」页处理本人刚生成且 AI 检查通过的题目，可在提交前微调并选择管理员配置的审核流程；保存只生成新版本，不触发 AI 复检。专家退回的题目只在「待我修改」页处理，提交修改后沿用原流程重新送审。
- **审核结果页**：`/review-results` 统计（通过/驳回/需修改/待决断等）+ 找出问题题目 + 每题的专家评语与最终决断
- **题库导出**：题库页按 100 道页码分页，支持跨页勾选和全选全部筛选结果；Excel/Word 只导出 `published/已通过` 题目，字段不含命题人列或机构占位符，并记录导出审计
- **列表工作区**：题库、AI 检查左栏采用固定搜索/操作区 + 独立纵向题目列表；题库卡片的状态/删除使用固定操作列，不受长题干裁剪影响；1280px 常用桌面宽度和 800px 窄屏均不再出现内容区横向拖拽
- **固定分页**：题库、知识点主表、知识点选择器、题库管理添加结果均采用“中间列表滚动 + 底部分页固定”，翻页后自动回到列表顶部
- **健康检查**：`GET /health/live` 仅检查进程存活；`GET /health/ready` 以 2 秒超时检查 PostgreSQL 与关键 Schema，不暴露 DSN/SQL 错误；`start.sh` 使用 readiness 判断后端启动成功
- **版本化迁移**：`schema_migrations` 保存版本、名称、SHA-256 校验和和应用时间；`go run ./cmd/aigo migrate` 独立升级，事务回滚 + PostgreSQL advisory lock 保证失败与并发安全；其他命令拒绝在未迁移、断档、过新或校验和不一致的数据库上运行
- **正式运行**：`build-production.sh` 生成Go二进制 + Vue静态资源的不可变版本release，`output/production` 指向当前版本；`run-production.sh` 以前台单进程同源提供页面和API，默认开启低权限自助注册、禁用项目 `.env`，运行阶段不需要Node/Vite，也不管理外部PostgreSQL
- **容器部署**：`Dockerfile + compose.production.yaml + deploy/` 已提供单机构部署骨架；应用非 root/只读根文件系统，PostgreSQL/输出/证书使用持久卷，迁移为一次性服务，Caddy 负责 HTTPS 和 JSON 访问日志，Secrets 以文件挂载
- **备份恢复**：独立非 root 备份服务立即+定时生成 custom archive，保存 SHA-256、版本元数据和稳定核心表指纹，按天数/份数清理；`deploy/backup.sh` 支持创建、校验、恢复演练、新库恢复和宿主机导出，禁止覆盖当前业务库
- **异机加密备份**：可选 `compose.offsite.yaml` 使用 `age` 公钥加密备份三件套并以不可覆盖模式上传 S3 兼容存储；上传后完整回读校验、receipt 最后提交，支持幂等扫描、状态重建、断网恢复、远端校验/下载和离线私钥恢复，主应用不保存私钥且不依赖该服务启动
- **账号防滥用**：Schema 3持久化独立账号/IP登录桶和注册IP桶；错误登录通用响应、短时指数限速、脱敏失败审计和dummy bcrypt防账号枚举；仅Compose内受控Caddy的客户端IP头可信
- **单题运行恢复**：Schema 23 新增 `generation_runs`，单题生成使用客户端运行 ID 做幂等控制，页面刷新后可恢复执行状态和结果；目前仍是长 HTTP 请求中的后台继续执行，不是可由新进程接管的持久 worker 任务

## 4. 技术栈

- **后端**：Go 1.22+（net/http 标准库路由 `method /path/{param}`），仅依赖 `lib/pq`、`excelize`
- **前端**：Vue 3 + Vite 7 + vue-router（Element Plus 未实际使用）；开发模式端口 5173 并代理 `/api`，正式构建由 Go 在同一地址托管
- **数据库**：PostgreSQL 16，基线 Schema 内嵌到后端；正式迁移由 `internal/storage/postgres/migrations.go` 管理，`start.sh` 先执行独立 `aigo migrate`，后端启动阶段只检查版本
- **LLM**：千问 OpenAI 兼容接口；实时生成/AI 检查配置由超级管理员在 Web “AI 服务配置”维护并加密落库，环境变量仅用于首次兼容导入/回退；当前可使用百炼 `qwen3.5-flash`，也保留本地 Qwen 3.5 服务接入
- **本地推理状态**：`QWEN_DEPLOYMENT=local`、本地 Base URL、served-model-name 和思考模式参数已经预留；本地模型服务、GPU 运行环境、容量评测和高可用尚未建设，不能把“接口可切换”视为“本地推理已可生产使用”。Web 批量已使用单题 API 队列
- **批量出题**：Web 管理端使用本地单题 API 队列，支持提交/轮询/导入和失败明细；CLI `batch-run/batch-status/batch-download` 保留 DashScope JSONL 任务兼容能力
- **测试工具**：后端 go test；前端 Playwright（anaconda python3，系统 Chrome 通道）

```text
  ↓
ai_draft（仅作为首次 AI 检查前的暂存草稿）
  ├─ AI 检查不通过 → 物理删除题目，淘汰原因单独留档
  └─ AI 检查通过 → ai_reviewed（待审核题库可见）
                         ↓ 管理员选择分类子题库和审核流程送审
reviewing（逐轮审核，每轮按配置的通过票数/一票否决规则推进）
  ├─ 全轮通过或发生分歧 → conflict → 把关人最终决断
  ├─ 需修改 → 任务 revision_required，题目恢复 ai_reviewed
  │              ↓ 自动进入原生成者「待我修改」
  │           修改并提交回库（版本+1，不触发 AI 复检）
  │              ↓ 管理员重新送审
  ├─ 驳回 → rejected 终态锁定，禁止修改和重新提交
  └─ 最终通过 → published（正式题库定稿）
                         ↓ 仅管理员可撤回
                     ai_reviewed 后再修订、重新送审
```

**关键规则**：
- AI 检查只在首次生成后自动执行一次，只能处理 `ai_draft`；任何人工修改都不触发复检，也不能回退 reviewing/published
- 送审、投票、最终决断、流程变更和撤销由 PostgreSQL advisory lock 跨进程串行化，防止并发丢票和同题重复任务
- 送审、投票、最终决断、退修重提、撤销和发布的审核记录/任务/题目状态使用同一 PostgreSQL 事务；失败整体回滚，跨进程锁继续负责并发串行化
- 每次题目内容变化生成不可变 `question_versions` 快照；审核任务绑定 `question_version`，版本不一致时拒绝投票/决断。状态和题库归属变化不新增内容版本
- 版本 2 迁移兼容旧表的 `id` 主键、`snapshot TEXT` 和 `changed_by` 列；执行 `aigo migrate` 时原位升级为 JSONB 并补 actor/change_type/唯一约束，不删除旧记录
- reviewing/conflict 题目禁止直接编辑；只有退回生成者的「待我修改」窗口允许修订，驳回题永久锁定
- **每轮按「通过票数」门槛推进**（如“1人通过即可”）：达到门槛即过轮；其他意见继续留痕并供最终把关人参考
- **把关人（决断者）只在所有轮次通过后出现**（最终待决断）；中途轮次出现分歧（全员投完仍有反对票）时才提前介入决断
- 最终轮决断通过 → 直接入库；分歧轮次决断通过 → 进入下一轮
- 终态任务（rejected/published）禁止再审核；conflict 任务禁止继续投票（只能决断）
- published 题目不能直接编辑；管理员必须先撤回到 `ai_reviewed`，修订后重新走人工审核
- 把关人（review:final）可审任意轮次；把关人名单按流程 `final_reviewer_ids` 快照校验
- 审核记录 ID 带时间戳，同一专家打回后可重审；决断记录同样留痕
- 提交审核写 submit/resubmit 日志，审核写 review 日志（含意见），全程留痕

## 7. 审核流程配置（可投入使用）

- 前端 `/review-flows`（flow:manage 权限）：新建/编辑/删除流程；专家在审核分组只显示「待我审核」，同时保留个人命题、待我修改和我的题库，不显示审核记录汇总和数据统计
- 流程字段：`bank_id`（固定适用分类子题库，空=不固定、送审时选择）、`final_reviewer_ids`（最终把关管理员名单，空=任意有「最终把关」权限者）、`rounds`（多轮，每轮 `expert_ids` 可为空 = 提交时按审题权限自动匹配）
- 后端校验（`review.CreateFlow/UpdateFlow`）：审核人必须是有审题权限的启用用户（或专家库历史记录兼容）、同轮去重、重复流程 ID 拒绝
- **编辑保护**：有进行中任务（reviewing/revision_required/conflict）的流程禁止修改/删除；有历史任务的流程禁止删除（保留追溯）
- 审核人选择：从「有审题权限的用户」中选择（`/api/review/reviewers`）；专家库页面已移除，由角色管理/用户管理替代
- 每轮可配置通过票数门槛和投票规则（通过票数推进/一票否决）；所有轮次完成后由把关人最终决断，中途未达标分歧会提前进入待决断

## 8. 权限体系（RBAC 可配置）

**权限模型**（`internal/domain/permission.go`，25 个权限点，提交审核为管理员专属不再设权限点）：

**题目可见性三档（2026-09-13 用户口径）**：
- 默认（无 question:view_all、未分配题库范围）：**仅本人题目**——不论角色，含下放管理员；历史无归属题仅 view_all 可见
- 授予 `question:view_all`（查看全部题库，权限矩阵可分配，超级管理员默认具备）：跨出题人查看全部题目
- **view_all 不随管理员角色默认下发（2026-09-13 用户口径）**：delegatedAdminPermissions 已排除该项——未授予时下放管理员同样只能看本人题目；需要跨出题人送审时由超级管理员在角色管理/权限矩阵显式授予。题库页对 view_all 持有者显示提示行（列表含所有用户题目，分享仅限本人）
- 分享至全局库只能由**题目所有者**发起（个人正式题，question:share + published + owner 校验，批量预览同样 OwnerID 限定）；他人可见 ≠ 可分享
- 直接分配题库范围（bank_ids 非空）：范围内题库的题目可见（含他人）
- 子题库目录随可见性收敛：普通用户只看到本人题目涉及的子题库，不再泄露全部子题库名录（如管理员自建测试题库）
- **子题库筛选已从题库页整体移除（2026-09-13 用户口径）**：题库页是个人/可见范围的三层浏览（专业/状态/难度/关键词过滤），子题库只出现在其职能场所——题库管理页（建库/归纳/移入移出/批量送审）与送审流程（提交时选定并快照）；全局题库与子题库无关（正式/淘汰题不可再调整分类）
- **删除即归档（2026-09-13 用户口径）**：published 或有审核任务史的题目删除改为置 `archived` 状态（进淘汰题库，标注"已归档"），版本快照/审核记录/审计链完整保留；仅无人工审核史的草稿与未送审题物理删除。守卫：审核中/待决断 409（先撤销或决断）、已淘汰终态 409、已提交全局分享 409（与撤回一致）。归档进**本人**淘汰题库（owner 不变）；全局淘汰题库唯一入口仍是"分享被拒"
- **全局题库三层口径（2026-09-13 确认保留）**：全局三层是分享申请状态的三种视图——待审核=分享待审批（curated 质量门，需求明确"分享仍需管理员审批"）、正式=批准、淘汰=拒绝（追溯分享被拒记录）；题目不"进入"全局库，只是按分享状态在不同视图可见
- 审核任务的题目内容由任务接口随载荷返回（reviewTaskAccess 授权），任务分配不放大题目浏览权限

- 用户可属于一个**角色模板**（roles 表，管理员可自定义 n 种角色）；也可**直接勾选权限点**（users.permissions）
- **有效权限 = 角色模板权限（全范围）∪ 直接分配权限（可带题库范围 users.bank_ids，空=全部题库）**
- 内置角色分为：`super_admin`（系统唯一超级管理员，完整权限，数据库唯一索引保证只能有一个）、`admin`（超级管理员分配的业务管理员，默认拥有除角色模板管理外的业务权限）、`expert`（个人命题/题库/退修/分享 + 分配任务审核，不含全局汇总和统计）和 `teacher`（命题）
- `role:manage` 只对 `super_admin` 生效；管理员可以增删普通用户、安排审核流程、管理题库并审核/决断，但不能创建第二个超级管理员、分配管理员身份或修改角色模板
- 超级管理员账号受保护，不能通过用户管理自我降级、禁用或删除；历史库中的默认 `admin` 账号启动时自动升级为 `super_admin`
- 每个用户拥有独立的正式/待审核/淘汰个人题库；题目接口按 `owner_id` 隔离，题目详情不返回出题人字段，审计日志和版本记录保留原始操作人
- 个人正式题目通过 `/api/questions/{id}/share` 申请进入全局库：`pending` 为全局待审核、管理员审批 `approved` 后进入全局正式、`rejected` 进入全局淘汰；每题唯一申请记录，不能重复申请
- 全局题库需要 `question:view_global`；申请需要 `question:share`，审批需要 `question:share_review`。管理员默认拥有全局查看与审批权限，普通客户默认只能看到自己的个人题库
- 审核记录汇总由独立的 `review:view_results` 控制，个人题库查看 `question:view` 不再自动开放审核记录页
- 管理员的数据统计默认进入全局范围，可切换“我的数据”；个人统计与全局统计分别按题目归属/分享状态聚合，避免个人题混入全局指标
- 题库范围权限点：查看/新建/编辑/删除题目、AI 出题、题库下载、审题、最终把关、统计分析（提交审核由管理员在题库页操作）
- 全局权限点：用户管理、角色管理、题库管理、审核流程配置、专家库管理（历史兼容，无独立页面）、操作日志、批量推理、知识点管理；批量推理和单题出题是两个独立权限点
- 内置角色模板：super_admin（权限固定，不可修改/删除）、admin（可由超级管理员调整业务权限）、expert（医学专家：个人命题与任务审核）、teacher（命题教师）
- **用户自主注册**（`POST /api/auth/register`，开关启用时登录页显示入口），注册后无任何权限，管理员在「用户管理」页按**权限矩阵勾选**分配（一列列打勾），并可选题库范围
- 用户可从左侧“个人中心 → 个人设置”或侧栏账号区进入设置，修改昵称并验证当前密码后修改密码；旧密码立即失效
- 权限检查从数据库实时读取，权限变更立即生效；禁用账号后 token 立即失效（JWT 仍 24h 但每请求校验启用状态）

**审核人匹配规则**：
- 流程轮次 `expert_ids` 显式指定 → 按名单审核
- `expert_ids` 留空 → 提交审核时自动收集**直接勾选「审题」权限且题库范围覆盖题目所属库**的用户（如内科分配 3 位老师 → 3 位都是审核人）
- 角色模板带来的审题权限不参与自动匹配（避免 admin/专家角色被自动拉进每道题）

## 9. 审核投票与最终把关

**逐轮推进**：每轮配置「通过票数」（required_count，0=全员）。达到通过票数 → 本轮通过：

1. 非最终轮通过 → 直接进入下一轮（专家审核正常进行，把关人不介入）
2. **最终轮通过 → 所有轮次完成 → 进入最终待决断（conflict）**，把关人此时才出现
3. 分歧处理：某轮全员投完仍未达到通过票数 → 该轮进入待决断，把关人决断
4. **最终把关人决断**（`POST /api/review/finalize`，需 review:final 权限）：
   - 把关人必须在流程 `final_reviewer_ids` 名单内（名单空 = 任意把关权限者；系统管理员 user:manage 不受限）
   - 决断 approved（分歧轮）→ 进入下一轮
   - 决断 approved（最终轮）→ **直接 published（已通过）**
   - 决断 rejected → 驳回并终态锁定；revision_required → 退回生成者修改，管理员重新送审后本轮票清零
5. 决断记录写入 review_records + 任务 final_decision 字段，全程留痕

**题目状态机**：

```text
ai_reviewed
        ↓ 管理员 SubmitQuestion（明确分类子题库，自动/显式匹配审核人）
reviewing ── 每轮按通过票数推进 ──┬─ 最终轮通过 → conflict（最终待决断）
                                  └─ 分歧 → conflict（待决断）
        conflict ── 把关人决断 ──┬─ approved（非最终轮）→ 下一轮 reviewing
                                ├─ approved（最终轮）→ published 已通过
                                ├─ rejected（终态锁定）
                                └─ revision_required（回原生成者修改，管理员重新送审）
```

## 11. API 摘要

- `/api/questions/{id}/bank` 手动移入/移出题库（bank:manage）
- `/api/knowledge-points` 列表/搜索（登录即可）/导入增删（knowledge:manage）
- `/api/experts` 列表 + 管理（历史兼容接口，界面已由角色管理/用户管理替代）
- `/api/review/reviewers` 有审题权限的用户列表（流程配置选审核人/名字映射）
- `/api/review/*` submit/submit-batch/action/finalize/task/task-by-question/records/flows（新题页按题批量提交本人题目；审核流程配置不再提供旧的题库批量送审/撤销入口）
- `/api/review/results` 审核结果汇总（统计+筛选+专家评语，question:view）
- `/api/review/my-tasks` 待我审核任务列表（仅当前轮分配给我的任务，投完即移开；题目进入下一轮会再次出现）
- `/api/review/my-decisions` 待我决断任务列表（review:final，独立「待决断」页面用）
- `/api/review/my-revisions` 原生成者的退修题列表（仅「待我修改」入口可编辑）
- `/api/ai-check` 检查进度/结果；手动补查按 question:edit，强制通过按 user:manage
- `/api/system/ai-providers` AI 服务配置（仅唯一 super_admin）
- `/api/export/xlsx|docx` + download（question:download，下载文件需认证）
- `/api/batch/*` 批量推理（batch:run）
- `/api/audit-logs` 日志（audit:view）
- `/api/stats` 统计（stats:view，含按题库/状态/难度分布）

`start.sh` 会先构建后端并独立执行 `aigo migrate`，迁移日志写入 `output/migrate.log`；随后通过公开健康接口确认 8080 后端真正就绪。数据库迁移或端口启动失败时会显示对应日志并退出，不会继续启动前端或虚报成功。

容器交付按 `deploy/README.md` 操作：复制生产环境模板、生成 Secret、检查 Compose 后启动。Compose 只公开 Caddy 80/443；数据库 5432 和应用 8080 不映射宿主机。本地 Qwen 是外部服务，必须填写容器可访问的内网地址。

备份服务默认启动后立即执行一次，之后每日运行，本地保留 14 天且最多 30 份。备份卷与 PostgreSQL 卷分离，但仍位于同一 Docker 主机；正式环境应按 `deploy/README.md` 启用独立 `offsite` 服务，在服务器侧用 age 公钥加密后自动上传对象存储。`drill` 只恢复到临时库并在指纹校验后删除，`restore` 只允许新的数据库名。

异机服务默认不启用，且从主 Compose 中分离，缺少 S3 配置不会影响现有应用、本地备份或恢复。应用服务器只保留 age 接收者公钥；私钥必须离线保存。客户端不可覆盖上传不能单独防删除，客户 bucket 必须开启版本控制和默认 Object Lock/WORM，并使用无删除、无绕过保留权限的上传凭证；本地模拟 S3 未验证真实 WORM，上线时必须单独验收。

## 19. 当前路线决策（2026-08-28）

### 19.1 已确认的产品与部署方向

- **题目形态**：当前只支持纯文本 A2 单选题。
- **文本推理最终走本地部署**：目标是在未来真实环境使用本地部署的 Qwen 3.5 模型服务；当前只完成了 OpenAI-compatible 接口和配置切换预留，尚未完成本地推理基础设施与生产验收。
- **最终面向真实多用户环境**：当前 `start.sh + Homebrew PostgreSQL + Vite dev server` 仅限本地开发，未来需支持多用户并发、长期运行、服务重启、权限隔离、任务恢复、监控、备份和升级。
- **近期按单机构多用户设计**：优先采用“一个客户/机构一套部署，机构内多个管理员、命题教师和审核专家”的交付形态。多个机构共享同一数据库的多租户 SaaS 需要额外的 tenant 数据隔离、租户级密钥/配额/审计和迁移策略，除非后续产品需求明确提出，否则当前不提前实现。
- **AI 仍是辅助命题工具**：AI 生成、AI 复核和 AI 修改都只能产生草稿或建议；任何 workflow/Agent 都不得绕过人工审核或直接发布正式题目。

### 19.2 Workflow 与生产部署的先后关系

当前不先引入 LangGraph、n8n、Dify、Coze 或自由自治 Multi-Agent。应按以下顺序推进：

```text
生产部署目标与运行边界
        ↓
正式部署基础 + 多用户安全/可观测
        ↓
持久任务层（重试、幂等、恢复、并发、运行记录）
        ↓
本地 Qwen 3.5 接入与质量/容量验收
        ↓
受控的生成—复核—修改 workflow
        ↓
小规模真实用户试点与指标回收
        ↓
```

原因：当前真正的阻断项是同步外部调用、开发态启动方式、缺少任务恢复和生产观测。直接先做 Agent workflow，会把多个不可靠的同步调用串成一个更长、更难恢复的调用链。近期需要实现的是 workflow 的**可靠运行底座**，而不是复杂的 Agent 编排框架。

### 19.3 引入受控 Workflow 的前置条件

只有满足以下条件后，才开始实现自动“生成—复核—修改”循环：

- 单次文本生成和 AI 检查已经任务化，进程重启后可继续或安全重试。
- 每次调用都有 run/step/attempt、题目版本、模型、prompt 版本、耗时、token 和失败原因记录。
- 本地模型已经完成固定医学 A2 题基准集评测和基本容量压测。
- 循环有确定性路由和硬上限，默认最多修改 1-2 次，失败后转人工或重新生成。
- 正式发布仍由现有审核事务、题目版本校验和人工最终把关完成。

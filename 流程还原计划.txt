5. 每完成一个实施阶段或发现设计变化，都更新本文件的勾选状态、证据、剩余问题及清理记录；不另建分散计划。

已由用户明确确认：
A. 保留题目当前内容和版本，只还原审核状态，不恢复早期正文，不重跑 AI 首检。
B. 待修改题不可执行审核还原；保存新版本后允许选择新的有效流程，但导致退修的原因和评语必须保留。
C. 审核还原删除旧送审、投票、决断类操作日志，保留生成、编辑和 AI 检查日志，并新增本次还原操作日志。

二、目标与严格状态边界

目标：管理员通过独立权限，把尚未结束的人工审核彻底撤销，使题目重新成为原出题人可修改、可另选流程送审的新题；不伪造 AI 通过，不变更内容版本，不牵连生成、正式题和分享流程。

可还原条件以“当前题目状态 + 当前最新任务”共同判断，不能只看某条旧任务：

当前题目 / 最新任务                         处理
reviewing / reviewing                       允许：任意轮次、0票/部分投票/已完成前面轮次均可
reviewing或conflict / conflict              允许：所有轮次已过、尚待最终决断；现有服务以任务状态为准，题目可能仍是reviewing
ai_reviewed / 无任务                        不允许：已经是未送审新题，不重复记还原成功
ai_reviewed / revision_required             不允许：进入待我修改；按独立的退修换流程路径处理
revision_required（历史兼容状态）            不允许在还原页操作，归入退修路径
published（含旧 approved 生命周期别名）      不允许；现有正式题撤回及分享规则不改
rejected / rejected                         不允许；驳回终态不能通过还原复活
archived                                    不允许；归档不能通过还原复活
ai_draft / auto_checked / AI检查故障/淘汰     不允许；不能绕过首次 AI 检查
缺题目、无归属、无最新任务或状态矛盾          异常只读展示并说明原因，不猜测或批量强改

还原前检查已有首次检查通过证据；人工修订后 AI 结果版本落后是合法的，不要求 AI 再检查，也不要求结果版本等于当前内容版本。若历史数据缺失通过依据，按明确的数据异常处理，不能直接“强制通过”。

还原后必须同时满足：
- questions.status=ai_reviewed；内容版本 version 原值不变。
- id、owner_id、created_by、正文/选项/答案/解析、知识点快照、难度等内容、生成时间不变。
- question_versions 全部内容和数量不变；不新增内容版本。允许更新状态的 updated_at。
- 该题不再有人工审核任务、各轮结果、投票记录或最终决断；不能只清当前轮或只删最新任务。
- 原出题人“新题修改与送审”重新出现该题，能修改保存，也能不修改直接选择有效新流程送审。
- 不进入待我修改；原审核人/把关人的旧任务消失；个人待审核题库仍保有该题，显示未提交审核。
- 原生成任务、批量检查点、首检任务/结果、模型配置、配额及已完成生成数量均不回退、不重建。
- 全局题库不会因还原而增加私人过程题，正式/淘汰题库和分享记录不被改写。

“首次状态”是未送审的业务状态，不是把当前题目 v3 改回 v1。后续正常编辑才增加内容版本。

三、源码调查与已确认的跨模块冲突

1. 新题可见性并非仅由 status 决定。
   internal/api/handler_question.go: handleMyNewQuestions 使用 ai_reviewed + owner_id + NoReviewTask。
   internal/storage/postgres/store.go: NoReviewTask 是 NOT EXISTS 任意 review_tasks。
   结论：只改状态、留下归档占位任务，题目仍不会回到新题工作区；只删最新任务又可能让更早任务重新浮现。

2. 工作台和导航使用多种口径。
   handler_auth.go: handleMySummary 的新题数也用 NoReviewTask，“我已审核”从 review_records 计算。
   reviewing→ai_reviewed 都属待审核层：层总量不能下降，但未送审数量应上升，审核人数值按删除的真实记录下降。
   审核记录汇总的 pending 状态由题目和最新任务联合推导，不能保留旧流程名或旧态度。

3. 模板引用与在途引用是两层守卫。
   review.Service.AssignmentReferencesByPermission 同时返回 FlowReviewDo/FlowReviewFinal 与 ActiveReviewDo/ActiveFinal。
   handler_auth.go 的用户更新/停用/删除、角色模板收权均使用这些引用。
   结论：任务清空后，仍留在活动流程模板中的专家会继续被旧守卫锁住；必须明确改为在途硬守卫、模板失效提示，不能只删任务。

4. 若放松模板守卫，未来轮次又会成为漏洞。
   当前任务仅快照 AssignedTo 当前轮；流程中后续轮次和最终把关人还可能需要该账号。
   结论：有在途题时，仍需保护所有尚需执行轮次及最终决断资格；不能只检查当前轮名单就允许撤权。
   清空相关在途题后，模板引用不再硬拦截；但该流程在资格失效时必须阻止新的送审。

5. 只检查第一轮的送审校验不够。
   submitQuestionLocked 当前只校验第一轮；后续轮次推进时才 resolveReviewers。
   结论：放松模板收权后，送审前必须检查全部轮次和指定把关人，防止第一轮正常、第二轮无人可审。

6. 待修改换流程不能只去掉一条 if。
   当前退修重送强制 existing.FlowID==flowID，并复用旧任务、递增 attempt。
   PostgreSQL SaveTask 的 ON CONFLICT 不更新 flow_id。只改服务判断，会出现内存测试通过、数据库仍是旧流程。
   直接覆盖旧任务 FlowID，还会把旧评语错误展示为新流程产生。

7. 最新任务与历史退修要同时处理。
   MyTasks/MyDecisions 按最新任务去重；MyRevisions 和 OwnerInFlightQuestions 还会扫描旧 revision_required 任务。
   结论：换流程后不能把旧任务仍留为待修改，否则旧待修改、用户占用和流程删除守卫会继续存在。

8. 审核历史删除不是只删 review_records。
   review_tasks.round_results、final_decision 也含人工意见；audit_logs.detail 还可能复制同样评语。
   必须按确认范围清理三处，且不能删除 AI review_results、版本、生成/编辑日志。

9. 当前审核动作与审计部分不在同一锁/事务内。
   送审/轮审/决断服务提交并释放审核锁后，handler 才写 submit/review/final_* 日志。
   结论：还原即使已清日志，旧请求仍可能迟到补写。必须把审核业务和相应日志放进同一审核写入边界。

10. 保持内容版本不变会出现状态来回切换的并发问题。
    老页面读到“未送审 v1”，其他请求送审→管理员还原→仍是“未送审 v1”。
    若只校验 version，迟到的旧送审/编辑请求仍可能成功，把题重新送回旧流程。
    结论：需要独立且单调递增的内部审核修订号，不能拿内容版本代替。

11. 前端现在不具备所需跨账号自动收敛能力。
    ReviewPage/ReviewDecisionsPage/NewQuestionsPage/MyRevisionsPage 主要在 onMounted 加载。
    SidebarNavigation 主要靠同页事件、身份变化和切路由刷新，不是服务端实时推送。
    结论：只在管理员页面发本地事件，其他浏览器中的专家任务不会自动消失。

12. 管理员默认不等于拥有全部私人题库查看权。
    新页面需单独授权读取“可还原的在途题及完整审核详情”，不能依赖 question:view_all，也不能全局放宽题库和普通审核接口。
    普通题目接口仍隐藏 created_by；只有新权限保护的管理 DTO 暴露出题账号信息。

13. 删除账号另有个人题目/生成/批量/分享占用。
    清除审核占用不等于可以删除仍拥有个人题目的出题账号；这些原有守卫继续保留。
    存在待修改题时，本页“全部可还原”也不能使流程一定可删除；待修改需先重送到新流程或完成处理。

14. 旧 API 错误与缓存必须同步适配。
    已删除 task_id 的迟到投票/决断应明确返回任务失效，不得500、重建任务或记成成功；旧列表/详情响应不能覆盖新状态。
    题库、统计、审核记录、日志、工作台及用户/流程弹窗若仍开着，也需要刷新与失效处理。

四、权限与数据访问设计（拟实施）

- 新权限：PermReviewRestore / review:restore，显示名“审核还原”，归“审核”，全局业务能力，不绑定旧分类子题库。
- 默认超级管理员和内置管理员拥有；教师、专家默认没有。沿用角色/直接授权体系，可按需授权自定义岗位，不硬编码只有角色名称 admin 才能使用。
- 模板初始化补齐新默认值，不改变既有 batch:run、role:manage、question:view_all、生成配额等权限边界。
- 菜单、路由、列表、详情、预览、单题与批量写入均检查当前身份实时权限；账号其他身份的权限并集不能放行当前身份。
- 授权者仅能查看本功能所需在途题、作者、知识点、流程和各轮意见；不顺带获得正式题导出、全局分享、用户管理或一般题库全员浏览权。
- 没有权限先403，再做对象查找/占用检查，避免错误信息泄露题目和专家。
- 权限被收回、身份被移除或账号停用时：关详情和确认框、清缓存、停止轮询，后端再次拒绝提交。
- 失去权限的管理员旧 token 和旧浏览器权限缓存必须即时失效，不等重新登录。

五、数据模型、事务及并发设计（拟实施）

5.1 内部审核修订号与历史血缘

拟为题目增加 review_revision（名称最终以实现统一），初始0，管理员还原时由数据库原子加1。
这是内部并发控制字段，不是题目内容 version，不显示成客户的新版本，也不允许客户端指定新值。
新题/退修的送审和编辑请求携带读取时的 expected_review_revision；旧请求即使内容 version 相同，也不能跨过一次还原。
普通保存、历史版本恢复、生成/批量重放和 AI 完成回调不得把该值覆盖回旧值；内容比较应排除该元数据，状态变化不生成 question_versions。

退修重送拟创建新审核任务，旧任务结束占用并保留记录；用 previous_task_id 或等价的明确血缘字段连接两次送审。
旧流程ID、退修意见、题目版本和旧批次不能被写成新流程的元数据。
新增字段与必要索引通过当前 LatestSchemaVersion 的下一版前向迁移实施，更新 schema、扫描、内存存储、契约和迁移测试；不改已有迁移 checksum。

5.2 还原操作边界

统一使用数据库审核 advisory lock → 单事务 → 按稳定顺序锁题目/最新任务 → 重新校验 → 清理/更新/审计 → 提交 → 释放锁。
送审、编辑、审核、最终决断、还原、流程删除和相关资格变更使用兼容锁顺序；不能部分路径先持事务/行锁、另一部分先取审核锁导致死锁或连接池耗尽。
API requireAuth 的检查之外，进入写入临界区后再次确认操作者当前资格。

事务内逐项完成：
a) 校验预览绑定的题目ID、最新 task_id、当前审核修订号、内容版本、范围/流程和必要的任务更新时间。
b) 确认当前仍是可还原状态，未被他人最终通过/驳回/退修；原出题人仍有可登录并编辑/送审的有效身份。
c) 获取实际会清除的任务、人工记录、旧审核类日志数量，供准确审计；不依赖前端提供的条数。
d) 删除该题所有人工审核任务，利用外键级联删除记录，并清理历史兼容孤立记录；清理旧轮次/决断不能留下占位任务。
e) 按明确动作白名单清除该题旧送审/重送/轮审/决断等审核类操作日志；不得按最近时间、操作人或模糊字符串批量删除。
f) 仅把题目状态改为 ai_reviewed、推进 review_revision、更新状态时间；保留正文、版本、所有权和首次检查。
g) 写 review_restore 操作事件，记录操作人、原因、题目、旧流程/轮次、实际清理数量、操作ID及时间；不把被删评语全文再复制到新日志。
h) 任意一步失败全部回滚，包括日志删除失败、还原事件写失败、客户端取消与超时等路径。

白名单实施前盘点实际 action 目录：submit/resubmit/review/final_*、旧 submit_bank/flow_revoke/本次历史迁移等按“题目级审核过程”分类。
流程配置的 flow_create/flow_delete 是另一类对象操作，不能因还原某题而删整条流程的管理日志。
生成、编辑、AI、模型、用户、规则、导出和分享类日志不在还原清理集合；既有还原事件作为独立操作事实保留。

原审核人已停用/撤权、旧流程已归档，不能成为“无法还原”的理由；这正是要解除的审核占用。
原出题人缺失或已不能编辑/送审时，页面显示具体原因，要求先恢复归属人可处理条件，不能静默转给管理员名下。
存在分享关联或正式/过程状态矛盾的异常题不由本功能更改分享，应只读提示单独处理。

5.3 单题、选中多题、流程全部与重试

- 单题与批量共用同一服务原语，不能分别拼不同SQL。
- 确认前预览真实影响范围；执行绑定这次预览的 task_id 和审核修订号集合，不能点击确认时重新扫全流程并把刚送来的题一起删掉。
- “全部”是该流程跨全部分页的全部可还原题，不是当前20条，也不包括驳回/正式/待修改等排除项。明确显示可还原数量和排除类别数量。
- 预览可用短时签名的选择凭证绑定操作者、身份、流程、候选集合和过期时间；执行时仍重新授权和校验状态，不持有长事务等用户点击。
- 选中批次全有或全无：任意对象权限/状态变化，返回409及需刷新的原因，不能悄悄部分删除；用户刷新确认后再执行。
- 每次操作有独立 operation_id；网络断开后同ID重试只能返回同次结果，不能再次还原后来新建的审核任务。不同载荷复用同ID拒绝。
- 新任务使用新 task_id；旧任务ID永不复用。旧投票/决断/重送请求失效后不得复活任务或迟到补写旧日志。
- 批量采用集合查询、集合删除、批量审计写入，不能逐题调用N次HTTP造成部分成功或长时间N+1。
- 分档验证1/20/100/500/1000题，补充5000题纯存储负载。同步批量上限根据实测确定并公开显示；超过上限明确要求分批，绝不把前N条称为“全部”。较大规模是否需后台任务另行决策，不先引入复杂新队列。

六、待修改换流程的独立处理（拟实施）

1. 继续在原出题人“待我修改”，不提供管理员审核还原按钮；只读保留退修原因和结构化评语。
2. 仍要求保存新版本，q.version 必须高于该次送审绑定版本；只改选流程但未修改保存，仍拒绝重送。
3. 增加流程选择；默认可沿用原流程，也可选择另一条当前有效流程。旧流程失效/归档时显示原因，允许选新的健康流程，不继续无条件强制原流程。
4. 同流程与换流程重送统一按新的送审批次处理：旧任务结束为不占用的历史状态，保留原 FlowID/全部记录/退修意见；新任务从目标流程第一轮开始，明确关联 previous_task_id，attempt 按前次递增。
5. 历史状态的显示用“已重送/已换流程”，不能让用户误以为整道题被归档。MyRevisions/OwnerInFlight/流程占用均不能再把旧任务算成进行中。
6. 历史展示按题目→任务/流程→批次→轮次组织，读取多个任务；不能只读最新task的记录。历史没有记录的版本/时间字段不编造。
7. 出题人至少能继续查到导致退修的原因；新的普通审核人仍遵循进行中意见隔离，不能借历史接口窥看其他专家全部意见。正式终态后按原有权限开放完整记录。
8. 单题与批量重送都支持明确目标流程。批量确认应明确“统一改用某流程”或“各自沿用原流程”，不能混用页面全局选项和逐题旧值。
9. 选择无效/资格已变化的流程时不破坏旧退修任务、意见或版本；单题事务保证归档旧任务与建立新任务同时成功。
10. 换流程本身必须保留原因；如果后来对重送后的“在途任务”又明确执行审核还原，则按还原定义清除该题人工审核历史，确认框应说明清除的是全部人工送审批次。不能把“换流程保留”与“审核还原清空”混为同一种操作。
11. 已通过题本身不可还原；现有独立的正式题撤回/分享逻辑不改。若通过原有授权撤回后已进入待修改，其后续保存与重送沿待修改规则执行，不能绕过正式题撤回守卫。

七、用户、专家、身份与流程守卫（拟实施）

- 在途任务仍为硬占用：检查当前和后续尚需审核的轮次、最终把关及待修改后续处理要求，不能删除/停用/撤销必需资格制造无人可办任务。
- 清空某专家所有相关在途任务后，单纯被未使用模板引用不再阻止撤权/停用/删除；不自动改写模板名单、不自动补回被撤权限。
- 模板因此失效时：管理页标注具体缺人/失权原因；可选流程接口与送审服务均做全轮次和把关人预检，不能接受到一条后半程会卡死的流程。
- 用户直接授权、增删附加身份、自定义角色权限修改和删除、停用/删除用户均采用同一判断，不留通过另一入口绕过的路径。
- 多身份看真正有效权限变化：一个身份移除，但其他身份仍保留审题权，不误拦；临时切身份不等于永久撤权。
- 用户管理资格检查与实际写入需与审核变更串行，避免“检查无占用→别人送审→撤权成功”的竞态。
- 出题人编辑/送审的可达性需要保护，不能把失去新生成权限与失去处理旧题能力混为一谈；有其他有效身份时给切换引导。
- 超级管理员/自身账号保护、管理员授权边界、个人题目/批量/生成/分享占用守卫保留。还原后不会允许删除仍拥有个人题目的教师。
- 流程全部可还原题清空后，若没有其他 reviewing/conflict/revision_required 引用，可以按现有行为删除归档该流程；有其他待修改仍说明具体阻挡，不承诺强删。
- 新旧流程历史通过归档配置继续解释；换流程后保留历史意见不应继续占用旧流程的在途名额。

八、前端页面、同步与统计设计（拟实施）

8.1 新页面

导航“审核工作 → 审核还原”，拟路由 /review-restore，组件 ReviewRestorePage.vue。
上方按流程、出题人、当前状态/轮次、题目关键词筛选；只显示该功能可管理的在途题；流程选项应包含仍有在途任务的已归档流程，避免旧数据无入口。
左侧/表格分页20条，可勾选；右侧详情显示题干、选项、答案、知识点快照、出题账号与姓名、当前版本、流程/轮次、当前分配及后续各轮名单/把关人、全部当前人工审核记录。
时间标签区分生成时间、任务建立时间、最近流转时间；没有独立重送时间的历史数据不假装知道精确送审时间。
记录按批次、轮次并列显示；有新权限的管理者能读完整评语，普通审核页面意见隔离不放松。

提供“还原当前题”“还原所选N题”“还原此流程全部N道可还原题”。无流程筛选时不提供含糊的全系统一键清空。
确认弹窗列明流程、数量、作者分布、实际会删除的记录范围，提示内容/版本/AI保留，人工审核记录和旧审核日志清除，填写简短原因。
执行中禁用重复提交；成功后清空过期选择和详情、回到有效页；空列表、读取失败、部分筛选无结果分别展示。

8.2 跨账号和多页面收敛

同页面动作事件可立即刷新；同一浏览器多标签可用 BroadcastChannel/storage 通知；不同账号、不同设备仍须服务端查询兜底。
采用共享、可取消、仅可见页面运行的轻量刷新协调器，合并同账号摘要请求，目标在可见且网络正常时5秒内收敛；回到前台立即刷新。
候选/审核/决断/新题/待修改、工作台、侧栏、题库、审核记录、统计、日志、流程/用户占用弹窗均列入刷新影响清单。
不要每个组件各自5秒触发全部摘要：现有工作台审核累计有N+1读取，需合并请求并对新增压力做SQL/性能验证；必要时对受影响聚合查询做小范围优化。
刷新不得覆盖正在编辑的正文或正在写的审核意见；任务被还原/资格收回时禁用旧提交，说明失效并刷新列表，不让旧表单写到新任务。
旧页码归位；切账号/切身份/撤权/退出时取消请求、清空敏感详情和确认token。所有请求绑定身份和请求代数，迟到响应不能覆盖较新数据。

8.3 一致性校验向量

一次还原N题后，逐账号、逐层对照同一数据库快照：
- 题目总数/生成数不变；内容版本和版本快照不变；AI通过数、首检次数、配额占用、批量导入数量不变。
- 原作者待审核层总数不变；未送审新题数+N；正式/淘汰数量不变；待修改数不变。
- 专家待审减少的是自己当前轮尚未投票的对应任务数；已投过当前轮的人原本没有该待办，不应多减。
- 待决断只减少被还原的 conflict 任务；尚在轮审的题不应错误扣一次决断。
- “我已审核”按被删除的本账号真实记录数减少；审核记录汇总回到未提交，原审题人基于参与记录的列表不再保留该题。
- 日志旧审核动作计数减少，本次还原事件增加；生成/编辑/AI等动作不变。日志不作为题目或审核统计的旁路事实源。
- 私人题仍归原作者；其他人的个人题库不增加；无分享不进入全局库；原有正式/分享数据不变。

C 并发交错（使用屏障/可控延迟，不靠随机sleep碰运气）
C01 专家最后一票先提交 vs 管理员还原先提交，两种顺序结果都合法且唯一。
C02 最终通过/驳回/退修先提交时还原失败；还原先提交时旧决断失效，不能再发布。
C03 两个管理员同时还原同题/重叠批次，不重复删新任务、不重复成功事件。
C04 同version的旧送审在“送审→还原”后放行，必须被review_revision拦截，不能送回旧流程。
C05 旧编辑/旧退修重送在还原/再次送审后放行，不能覆盖新状态；正常保存内容版本仍严格递增。

C07 还原和撤权/切身份/停用/删除/流程归档交错，前端与后台共同遵守同一资格状态。
C08 预览以后新增题、投新意见、轮次推进、版本变化，执行只处理经再次确认的一致集合。

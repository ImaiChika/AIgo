====================================

一、先给结论
------------

1. 当前项目不适合一开始就上 Kubernetes、Redis、微服务或多机集群。现阶段更合适的路线是：先把单机的可观测性、限流、背压、数据库查询和异步队列做好，再根据压测证据决定是否扩容。

2. 当前架构已经具备一部分良好基础：Go 服务、PostgreSQL、持久化生成队列、持久化 AI 检查队列、FOR UPDATE SKIP LOCKED 抢占、租约与重试、请求体限制、分页、健康检查、Caddy 压缩与静态资源缓存、Docker 资源限制、数据库事务和 CI 竞态测试。这些都应保留，不做大规模重构。

3. 当前最主要的高并发风险不是 Go 本身，而是：
   - 没有真实容量基线和运行指标，无法知道先满的是 CPU、内存、数据库、磁盘还是千问额度；
   - 普通 HTTP 请求、生成任务和批量任务缺少统一的准入、限流与队列上限；
   - 单题生成、批量生成、AI 检查分别限并发，但共用模型端点时没有共享的总并发预算；
   - 每个认证请求存在多次数据库查询，AI 检查进度等接口存在逐题查询，容易在用户轮询时放大数据库压力；
   - 批量任务每完成一题就重写整份 JSON 结果，任务越大，数据库写放大越严重；
   - 导入、导出仍是同步重任务，可能同时占用内存、CPU、磁盘和数据库连接；
   - 当前本地批量执行器只适合单应用实例，若直接横向启动多个 app 容器，可能重复恢复和执行同一批量任务。

4. 对小服务器而言，“高并发适配”的目标应是过载时可控：请求可以排队、限速或明确拒绝，但不能把数据库拖死、重复出题、重复扣费、破坏审核状态或造成全站不可用。


二、高并发必备知识点
--------------------

1. 并发、吞吐与延迟不是同一个概念

   - 并发数：同一时刻正在处理或等待的请求/任务数量。
   - 吞吐量：单位时间内完成的请求或任务数量，常用 QPS、任务/分钟表示。
   - 延迟：一次请求从进入到完成的时间，应重点看 p95、p99，而不只看平均值。
   - Little 定律：系统内平均并发量 L = 到达速率 λ × 平均停留时间 W。AI 调用耗时很长，即使 QPS 不高，也会积累大量并发等待，因此 AIgo 必须依赖异步队列和背压，而不是无限增加 goroutine。

2. 高并发首先是容量管理问题

   系统容量由最先饱和的资源决定，常见瓶颈包括 CPU、内存、数据库连接、慢 SQL、磁盘 IOPS、网络连接、文件句柄、外部 API 限额和外部模型响应时间。必须先测量再调参，不能只通过“增加连接数/worker 数”解决问题；连接和 worker 过多反而会造成内存上升、上下文切换、数据库争用和模型限流。

3. SLO 与错误预算

   高并发优化必须先定义目标，例如普通查询 p95/p99、任务提交延迟、允许错误率、AI 队列等待时间和任务完成率。没有目标就无法判断“够不够快”，也无法判断是否需要扩容。AI 接口应把“快速入队”和“后台完成”分成两个指标，不能把外部模型耗时混入普通 HTTP 接口目标。

4. 限流、并发闸门、背压和降级

   - 限流：限制单位时间的请求量，保护系统和费用预算。
   - 并发闸门：限制同时执行的重任务数量，避免 CPU、内存、数据库或外部模型被打满。
   - 背压：下游忙时让上游排队或减速，不继续无限接收任务。
   - 负载卸除：队列已满时返回 429/503 和 Retry-After，宁可明确拒绝，也不能让全站雪崩。
   - 降级：高负载时可延后非关键统计、导出和批量任务，但不能绕过 AI 检查、审核权限或正式题库密封规则。

5. 队列的核心语义

   队列要明确任务状态、最大队列长度、优先级、公平性、重试、退避、超时、租约、死信/耗尽状态和取消规则。数据库队列常用 FOR UPDATE SKIP LOCKED 抢占。分布式系统通常只能实现“至少一次”执行，因此任务必须幂等，不能假设绝对只执行一次。AIgo 已采用租约和幂等方向，应继续加强而不是另起一套队列。

6. 幂等、事务与并发正确性

   - HTTP 重试、浏览器重复点击、进程重启和网络超时都可能导致重复提交。
   - 幂等键、唯一索引和条件更新是防重的第一道保障。
   - 需要原子完成的业务必须进入同一事务，例如题目状态、审核记录、任务状态和审计记录。
   - 长事务会占用连接和锁；外部模型调用绝不能放在数据库事务里。
   - 乐观锁适合知识点/题目版本更新，行锁适合短时间抢占和最终决断。

7. 数据库高并发基础

   - 连接池必须与 PostgreSQL 最大连接数、服务器内存和应用实例数一起计算。
   - 必须消除 N+1 查询、无界列表、深 OFFSET 分页和不必要的全表扫描。
   - 索引应由真实 SQL、数据分布和 EXPLAIN (ANALYZE, BUFFERS) 决定；索引太多会拖慢写入。
   - 高频条件与排序通常需要组合索引；模糊搜索可使用 pg_trgm，但要确认生产库扩展和索引确实存在。
   - 统计类查询适合短 TTL 缓存、预聚合或异步计算，不能每次页面刷新都重复扫描大表。

8. 缓存的正确使用

   缓存适合读多写少的数据，例如知识点目录、角色模板、活动 AI 配置和统计摘要。缓存必须定义 key、TTL、容量和失效方式。权限缓存不能只靠长 TTL，否则管理员收权后可能延迟生效；应优先做“单请求内只查询一次”，再考虑带版本号/主动失效的短缓存。

9. 水平扩展的前提

   多实例要求运行状态外置：任务归 PostgreSQL/队列，文件归共享存储或对象存储，缓存能跨实例失效，限流有全局口径，定时任务和恢复任务不能被每个实例重复执行。只把 app 容器复制两份并不等于可安全扩容。

10. 可观测性与压测

    必须同时具备指标、结构化日志、请求 ID、慢 SQL、队列指标和资源指标。压测至少包括基准、阶梯加压、峰值、长稳、故障注入和恢复测试。压测不能直接在唯一生产环境上无保护执行，应在本地隔离环境或生产同规格的临时环境进行。


三、当前项目的并发架构盘点
--------------------------

1. 部署形态

   - 线上是单台阿里云 ECS，/opt/aigo 下由 Docker Compose 运行 app、PostgreSQL、Caddy、backup；80/443 只暴露 Caddy，app:8080 与 PostgreSQL:5432 位于容器网络。
   - 当前示例资源限制为 app 1 GiB/2 CPU、backup 512 MiB/1 CPU；PostgreSQL 与 Caddy和它们共享同一宿主机。实际宿主机 CPU、内存、磁盘类型、剩余空间和数据库参数仍需在计划第一阶段采集，不能用 Compose 限额代替真实容量。
   - 服务器 production.env 和 deploy/secrets 是唯一生产权威源，本地副本不能反向覆盖；后续任何同步仍须排除这两类文件。

2. HTTP 与静态资源

   - Go http.Server 已配置请求头、读、写和空闲超时；请求体默认限制 10 MiB，知识点导入单独限制 32 MiB。
   - Caddy 已启用 zstd/gzip、安全响应头、健康检查和 JSON 访问日志；Vite 指纹静态资源使用一年 immutable 缓存。
   - 当前没有全站/分路由的请求速率限制、最大在途请求数、排队上限和 Retry-After 语义。

3. 数据库

   - database/sql 当前固定 MaxOpenConns=10、MaxIdleConns=5、ConnMaxLifetime=5 分钟。
   - 已有题目状态、创建时间、owner+status、审核任务、批量任务、AI 检查任务等索引，也尝试启用 pg_trgm。
   - 题目搜索使用 COUNT + LIMIT/OFFSET；深分页成本会随页码增加。
   - 认证中间件为保证停用和收权立即生效，每个请求实时读取用户、角色和有效权限；当前实现会产生多次 SQL，安全性正确但在高并发下成本偏高。

4. AI 与后台任务

   - 单题生成已是 PostgreSQL 持久化队列，固定 2 个 worker，使用 SKIP LOCKED、租约、重试和幂等 run_id。
   - AI 检查是 PostgreSQL 持久化队列，默认 2 个 worker，可配置 1–32，并有超时、指数退避、租约和每题唯一任务索引。
   - 本地批量执行器默认全局并发 2，但每个批量任务启动一个 goroutine，并在内存中顺序处理该任务；服务重启时扫描并恢复 in_progress 任务。
   - 三条通道在默认配置下可能同时向同一个千问端点发出约 2（单题）+2（批量）+2（检查）个调用，缺少共享总预算和按用途公平调度。

5. 前端轮询

   - 单题生成运行状态约每 2.5 秒轮询；AI 检查进度默认每 5 秒轮询；批量任务正常每 10 秒轮询，失败后 30 秒。
   - 页面隐藏时已有部分停止轮询逻辑，这是良好基础；但多用户同时等待生成/检查时，轮询会形成稳定的数据库读流量。

6. 已发现的数据量放大点

   - 服务启动为补建 AI 检查任务会先 ListQuestions 全量加载题目。
   - 批量“跳过已有题目”会全量加载题目后在 Go 中筛选本人题目。
   - AI 检查进度最多接收 500 个题目 ID，服务层和接口层均存在逐题 GetQuestion/权限判断，形成明显 N+1 查询。
   - 审核待办虽然已在 SQL 预过滤，但仍先装载全部匹配任务后在 Go 中分页；任务量大时每次只展示 20 条却处理更多数据。
   - 统计页一次请求执行多组聚合；全局用户数当前通过加载全部用户再取长度。
   - 导出全部筛选结果会全量读取题目并在 Go 中过滤、同步生成文件；勾选导出也逐题查询。
   - 批量任务每完成一个单元，就序列化并更新包含所有 Questions/Items 的 output_json；大任务会产生 O(n²) 级别的累计序列化和数据库写放大。
   - 批量结果导入逐题 SaveQuestion，再逐题查询并入队 AI 检查，数据库往返较多。
   - 批量列表 limit 没有统一的服务端最大值；单题生成接口未在后端强制与前端 1/3/5 道的选择上限保持一致；批量虽限制每知识点最多 20 道，但没有限制任务总题数和用户活跃任务数。

7. 横向扩展阻碍

   - 单题生成和 AI 检查队列可由多个 worker 实例安全抢占。
   - 当前本地批量执行器没有数据库级逐项抢占/租约；多个 app 实例启动时都可能恢复同一 in_progress 批量任务，不能直接多副本运行。
   - 知识点缓存是进程内缓存，跨实例修改最长可能等待 TTL；需要跨实例失效机制。
   - 导出文件保存在当前宿主机的 app_output 命名卷；同机 Compose 副本可以挂载该卷，但跨主机副本不能直接共享，后续多机时必须迁移到共享卷或对象存储。
   - 若未来使用进程内限流，多实例后也会失去全局限制能力。


四、问题优先级
--------------

P0（先做，否则无法安全压测或应对突发流量）

1. 建立指标、慢请求和容量基线。
2. 增加普通接口与重接口的并发闸门、速率限制、队列上限和明确拒绝策略。
3. 把生成、批量生成、AI 检查纳入同一个模型调用并发/速率预算。
4. 限制单题数量、批量总题数、每用户活跃任务数、全局待处理任务数和导出规模。
5. 修复 AI 检查进度等最明显的 N+1 查询，并降低权限查询放大。
6. 让数据库连接池、HTTP 超时、优雅退出时间、worker 数量可配置且有安全默认值。
7. 增加输出目录容量、文件保留期和磁盘水位保护，避免导出文件拖满系统盘。

P1（单机容量优化）

1. 优化批量任务存储模型，避免反复重写整份 JSON。
2. 将审核待办分页、批量跳过已有、启动补扫、导出筛选全部下推数据库并批量读取。
3. 对统计、知识点元数据、角色模板和活动 AI 配置建立合适的短缓存/主动失效。
4. 用真实 EXPLAIN 补组合索引，治理深 OFFSET 和模糊搜索退化。
5. 将大导入、大导出改为受控异步任务或流式处理。
6. 优化前端轮询为带抖动的退避轮询，避免同一时刻形成尖峰。

P2（达到明确扩容阈值后再做）

1. 将 API 与 worker 运行角色拆开，但继续使用同一 Go 代码库和镜像。
2. 把批量执行改成数据库可抢占的 job_item 队列，完成多实例安全前置。
3. 导出文件迁移到共享卷/对象存储，知识点缓存增加跨实例失效。
4. 再考虑多个 app 实例、数据库独立主机/托管 PostgreSQL、Redis、读副本或 CDN。


五、分阶段实施计划
------------------

阶段 0：定义目标并建立基线（必须最先完成）

目标：知道系统在当前小服务器上“能承受多少、先坏在哪里”。

工作项：

1. 采集服务器事实：CPU 核数、内存、swap、磁盘类型/容量/IOPS、inode、网络带宽、Docker 版本、容器实际用量、PostgreSQL max_connections/shared_buffers/work_mem、数据库大小与主要表行数、千问端点并发/每分钟/token/费用限制。
2. 增加服务指标：按路由的请求数、状态码、p50/p95/p99、在途请求、响应体大小；数据库连接池 open/in_use/idle/wait_count/wait_duration；SQL 慢查询；三个队列的 pending/running/age/attempts/exhausted；模型调用并发、耗时、429、超时、token（若供应商返回）；进程 CPU、内存、goroutine、GC、文件句柄和磁盘水位。
3. 日志统一加入 request_id、user_id（内部 ID，不记录密码/token）、route、status、duration_ms、run_id/job_id/task_id；错误日志区分用户错误、系统错误、模型错误和限流拒绝。
4. 打开 PostgreSQL 慢 SQL 观测；只在内网/管理员边界开放 pprof，禁止公网裸露。
5. 记录无优化基线，并保存压测命令、数据规模和结果，后续每阶段用同一场景对比。

建议的初始 SLO（压测后允许修订）：

   - 健康检查：p99 ≤ 100 ms。
   - 普通列表/详情/权限接口：目标负载下 p95 ≤ 300 ms，p99 ≤ 800 ms。
   - 普通写操作：p95 ≤ 800 ms（不包含模型调用和大文件处理）。
   - 生成/批量提交入队：p95 ≤ 500 ms；外部模型完成时间单独统计，继续遵循产品“单题生成目标小于 1 分钟”。
   - 非预期限流外的 5xx < 1%；数据库连接等待不能持续增长。
   - 稳态 CPU 建议低于 70%、内存低于 80%、磁盘低于 75%，为备份、峰值和恢复留余量。

交付物：容量基线报告、指标看板、告警清单、第一版安全并发参数表。


阶段 1：单机入口保护与统一背压

目标：即使流量超过容量，也保持登录、题库浏览、审核和健康检查可用。

工作项：

1. 在 Go 中间件增加分层保护：
   - 轻接口：登录后详情、列表、审核操作；
   - 重查询：统计、复杂搜索、进度批量查询；
   - 重任务：导入、导出、生成提交、批量提交。
   每层独立设置最大在途数和超时，满载时返回 429 或 503，并附 Retry-After。
2. 按来源 IP、用户和接口建立速率限制；登录/注册继续保留现有数据库限速。单实例阶段可先使用有界内存令牌桶，但必须设最大 key 数和过期清理；多实例前再迁移到全局实现。
3. 增加任务准入：
   - 单题接口后端强制最多 20 道，与当前前端自定义输入上限一致（常用快捷值仍为 1/3/5）；
   - 批量任务设置“每任务总题数、每用户活跃任务数、全局待处理数”三个上限；建议首轮压测从每任务 500 道、每用户 1 个活跃批量任务开始，再依据吞吐调整；
   - 限制每用户未完成单题运行数，防止刷新/脚本无限入队；
   - 批量列表 limit、导出 ID 数量、进度查询 ID 数量都设置统一硬上限。
4. 建立共享模型并发控制器：生成、批量和检查不能各自只看自己的 worker 数。按照活动 AI provider 的额度设置总并发、每秒/每分钟速率和 429 退避；为互动生成、AI 检查、批量生成保留最低份额，并采用公平调度，避免大批量任务饿死单题和首次检查。
5. 把 generation worker 数、batch worker 数、数据库池参数、入口在途上限等改为环境配置；非法值应回退到保守默认值并打印脱敏配置摘要。
6. 优雅退出与容器 stop_grace_period 对齐。停止接收新任务后先停止抢占，允许短请求完成；未完成的长 AI 任务靠租约恢复。避免应用 15 秒退出、容器 30 秒终止与最长 90 秒/10 分钟任务之间没有明确语义。
7. 前端轮询加入随机抖动和逐步退避；浏览器页隐藏/路由离开立即停止。生成状态可从 2.5 秒逐步退到 5/10 秒，检查与批量继续根据状态退避。暂不需要为了轮询直接引入 WebSocket。

验收：超过设计流量时出现可解释的 429/503，队列长度有上限，数据库和审核接口仍可用，无重复题目、无重复 AI 首检、无越权降级。


阶段 2：数据库与热点接口优化

目标：减少每个请求占用的数据库连接和 SQL 次数，提高单机有效吞吐。

工作项：

1. 认证/权限：先把一个 HTTP 请求内的用户、当前角色、有效权限和范围一次性查询并放入 request context，后续 requireAuth/hasPermission/GetBankScope 复用，不在同一请求反复查库。跨请求缓存必须带权限版本或在用户/角色变更时主动失效，保证停用、收权立即生效。
2. AI 检查进度：一次批量读取题目、任务、结果、淘汰档案和归属信息，在内存中做一次权限裁剪；消除 service 与 handler 的双重逐题 GetQuestion。500 个 ID 的请求不应产生数百次 SQL。
3. 批量任务查询：
   - “跳过已有题目”改为按 owner_id + 大纲版本 + 知识点快照在 SQL 中查询；
   - 状态和任务列表直接在 SQL 中按 owner/status/name 过滤并限制条数；
   - owner 名称使用 JOIN/批量查询，避免逐任务 GetUserByID。
4. 审核：将待我审核/待我决断的总数、分页和必要关联下推 PostgreSQL，只读取当前 20 条；题目和记录批量查询。保持“同轮意见隔离、终态开放完整记录”的权限语义不变。
5. 启动补扫：用 status='ai_draft' 的专用 SQL 直接获取需要补建的 ID，不再启动时全量加载所有题目。
6. 统计：把多次扫描整合为更少的条件聚合；用户数用 COUNT；按 personal/global + 权限范围设置 5–30 秒短缓存，并在关键写入后失效。统计允许短暂延迟，但题目状态与审核操作不能使用过期缓存。
7. 搜索与分页：
   - 在生产确认 pg_trgm 和 search_text GIN 索引实际存在；
   - 对 owner_id/status/created_at、审核待办、AI 队列等用 EXPLAIN 验证组合索引；
   - 常用前几页可保留页码，深分页增加基于 (created_at,id) 的游标接口，避免大 OFFSET；
   - 只根据证据加索引，记录新增索引的写入成本和磁盘占用。
8. 数据库池：根据 PostgreSQL 内存和 app/worker 实例数计算 MaxOpenConns，而不是盲目增大。增加 ConnMaxIdleTime、池等待告警和查询上下文超时。连接池调优必须在慢 SQL/N+1 修复后进行。
9. 活动 AI 配置和角色模板：增加小容量、主动失效缓存，减少每次模型调用/权限计算的重复读取；API Key 仍只在受控内存中短时存在，不写日志。

验收：核心接口 SQL 次数有明确上限；500 ID 进度查询、20 条审核待办、100 条题库列表在目标负载下不出现线性 N+1；连接池等待和慢 SQL满足阶段 0 的 SLO。


阶段 3：批量任务、导入导出与存储治理

目标：消除大任务对内存、数据库写放大和磁盘的冲击。

工作项：

1. 新增 batch_job_items（或等价结构），每个生成单元单独保存知识点快照、状态、尝试次数、错误、生成结果和租约。worker 使用 SKIP LOCKED 逐项/小批抢占，不再为每个批量任务创建常驻 goroutine，也不再每完成一题重写完整 output_json。
2. 批量状态由 item 聚合或增量计数得到；保留旧 output_json 的兼容读取迁移期，采用“先双读/再迁移/最后停写”的扩展—收缩方案。
3. 题目落库、版本快照、AI 检查任务入队采用小批事务或 outbox 语义；每题仍只能有一个首次检查任务，失败重试规则不变。
4. 导出改为受控异步任务：提交后返回 export_id，专用低并发 worker 从数据库分页/游标读取并流式写文件；设置每用户并发、最大题数、文件最大体积、过期时间和下载鉴权。若暂不异步，至少先实现数据库筛选、批量 GetQuestionsByIDs、并发闸门和导出上限。
5. output/exports 增加定时清理和磁盘配额；磁盘达到告警/拒绝水位时停止新导出，但不能影响审核和题库读取。文件名继续保持不可预测/不冲突，下载继续做权限验证。
6. 大纲导入按版本加互斥，防止同一版本并发 merge/replace；大文件超过阈值改为异步校验。解析过程设置解压大小、行数、单元格和压缩炸弹防护，保持“所有文件校验成功后一个事务写入”。
7. 备份安排在低峰并限制资源；记录备份时延、数据库 I/O 和业务 p99，避免 backup 与大导入/导出同时把磁盘打满。

验收：500 道批量任务的数据库写入量近似线性；进程重启后仅恢复未完成 item；并发提交不会重复执行或重复导入；导出和备份期间普通查询/审核仍满足 SLO。


阶段 4：按证据拆分进程并横向扩展

进入条件：完成 P0/P1 后，在目标负载下仍持续出现资源饱和或业务明确需要高可用；不得仅因“可能高并发”提前实施。

工作项：

1. 同一镜像增加运行角色：api、generation-worker、ai-check-worker、batch-worker。先可在同一台机器分角色限额，真正有容量需要时再放到不同主机；不拆仓库、不复制业务代码。
2. 多 app 副本前必须完成：批量 item 数据库抢占、全局任务配额、跨实例缓存失效、共享/对象文件存储、唯一计划任务和多实例压测。
3. Caddy 可反向代理多个无状态 API 实例；JWT 本身无会话粘性要求。健康检查只反映 API/数据库就绪，不因模型临时不可用把全部题库浏览流量摘除。
4. 若同机 PostgreSQL I/O/内存成为瓶颈，优先把 PostgreSQL 迁到独立高性能磁盘、独立主机或托管服务，并建设 PITR；这通常比在同一小 ECS 上复制 app 更有价值。
5. Redis 只在出现以下需求时引入：多实例全局限流、跨实例热点缓存、可靠的短时协调。持久业务队列仍可继续使用 PostgreSQL SKIP LOCKED，不因流行而强制换队列。
6. 读副本只在读压力确实占主导且允许短暂复制延迟时使用；审核状态、权限、任务抢占和刚写后的详情必须读取主库。
7. Kubernetes 仅在多主机、多环境、自动扩缩、滚动发布和运维团队能力都成为真实需求时评估。当前单服务器 Compose 继续作为首选。


六、压测与故障演练方案
----------------------

1. 数据准备

   准备至少三档数据库：当前量、10 倍量、预期两年量。题目、版本、审核任务、记录、AI 检查结果、淘汰档案和审计日志都要按真实比例生成；不能只压空库。

2. 负载场景

   - 读场景：登录后工作台、题库列表/搜索/详情、知识点树、审核待办、统计。
   - 轮询场景：大量用户同时等待 generation run、AI 检查进度和 batch status。
   - 写场景：并发提交审核、多人同轮投票、最终决断、退修保存和版本冲突。
   - AI 场景：并发单题提交 + 大批量生成 + AI 检查 backlog 同时存在。
   - 文件场景：32 MiB 大纲导入、较大正式题库导出、备份同时运行。
   - 攻击/误操作场景：重复点击、相同幂等键、不同幂等键刷任务、超大页码、超大 limit、无效 token 和登录失败洪峰。

3. 压测方法

   - 阶梯：10、25、50、100、200 并发用户逐级增加，每级保持 10–15 分钟，找出拐点。
   - 峰值：在稳定容量的 2 倍流量下验证限流、队列上限和恢复。
   - 长稳：至少 2 小时，候选生产配置建议 8 小时，观察内存、goroutine、连接、磁盘和队列是否持续增长。
   - 结果按路由记录 p50/p95/p99、成功率、429/503、数据库等待、模型 429、队列最长等待和资源峰值。

4. 故障注入

   - 千问返回 429、500、超时和慢响应；
   - worker 执行中 kill/restart；
   - PostgreSQL 短时不可用/变慢；
   - Caddy/app 重启；
   - 磁盘接近拒绝水位；
   - 备份与导入/导出重叠；
   - 多人同时审核同一题、同时修改同一知识点。

5. 必须验证的业务不变量

   - 每道新题只创建一次 AI 检查任务；人工修改不复检；
   - AI 检查不通过的题目删除且淘汰原因留档；系统故障不误判为质量淘汰；
   - 未通过 AI 首检不能送审，未全轮通过不能进入正式题库；
   - rejected 终态不可修改/重提；退修必须保存新版本后从第一轮重审；
   - 正式题库权限、导出权限、个人/全局范围在限流和缓存下仍无旁路；
   - 重试、重启和超时不会重复生成、重复导入、重复投票或重复扣费。


七、本地—服务器同步实施与回滚流程
--------------------------------

1. 所有优化先在本地分支完成；执行 go test ./...、必要的 go test -race、前端测试/构建和压测。当前编制本计划时 go test ./... 已通过，但这不等于完成容量测试。
2. 数据库变更采用向前兼容的扩展—收缩迁移。大表加索引应评估锁表；当前迁移器默认每版本事务执行，若需 CREATE INDEX CONCURRENTLY，应先为迁移器设计受控的非事务迁移能力或独立上线步骤，不能直接塞入现有事务迁移。
3. 上线前执行并验证备份；保存当前镜像/构建版本、Schema 版本、配置摘要和压测基线。数据库是前向迁移，旧镜像不能被视为完整回滚，必要时必须结合备份恢复。
4. 同步到 /opt/aigo 时明确排除服务器 deploy/production.env、deploy/secrets、数据卷、备份卷和本地输出；服务器配置始终是权威源。
5. 先部署可观测性和只读优化，再启用限流/新队列；所有新限额使用环境开关和保守默认值，便于快速回退。
6. 发布后依次验收：health、登录、个人工作台、生成入队、AI 检查、审核、正式题库、导出、备份；再做小流量冒烟，不在唯一生产环境直接做破坏性满载压测。
7. 涉及 Caddy/域名时继续遵守 deploy/README.md 第 10 节：域名不可丢失，IP 必须保留 http:// 前缀，环境变量变化后用 compose up -d caddy 重建而不是 restart，并完成域名与 IP 双路径验收。


八、扩容决策门槛
----------------

1. 先优化代码：若瓶颈是 N+1、全表扫描、无界任务或同步导出，扩机器只会推迟故障。
2. 垂直扩容：优化后 CPU/内存/磁盘在目标负载下持续超过安全水位，且单机仍满足可用性要求时，先升级 ECS 或磁盘。
3. 数据库独立：PostgreSQL 与应用/备份争抢内存或 I/O、慢 SQL已治理但数据库仍是主瓶颈时，将数据库迁出同机。
4. 应用水平扩展：普通 API CPU 成为瓶颈，且阶段 4 的无状态前置条件已完成时增加 app 副本。
5. Redis/读副本：只有多实例协调或读压力的指标证明需要时引入。
6. 多机高可用：若业务要求单机故障不停服，必须承认当前“同一 ECS 上多容器”不具备主机级高可用，需要独立数据库、至少两个应用节点、负载入口和异机备份/恢复体系。


九、建议执行顺序与预计产出
--------------------------

第 1 批（P0，先保护系统）：阶段 0 + 阶段 1。
产出：容量基线、指标告警、请求/任务限流、共享 AI 配额、可配置连接池与 worker、轮询退避、过载可恢复。

第 2 批（P1，提升单机吞吐）：阶段 2。
产出：认证单请求一次加载、进度批量查询、审核 SQL 分页、统计缓存、索引与 SQL 报告、连接池调优报告。

第 3 批（P1，治理大任务）：阶段 3。
产出：batch_job_items 持久队列、批量落库/入队、异步导出、文件清理、导入互斥、备份错峰。

第 4 批（P2，按容量证据扩展）：阶段 4。
产出：API/worker 运行角色、多实例安全清单、共享文件方案、数据库迁移或多副本部署方案。


十、本计划明确不做的事
--------------------

1. 本轮不修改代码、数据库、环境变量、Caddy 或线上容器。
2. 不因高并发引入知识图谱、Neo4j、图片、多模态、复杂研究模块或历史真题重平台。
3. 不把审核流程写死，不改变题库分层和权限边界，不提供 AI 复检/强制通过。
4. 不在没有压测和指标证据时直接上 Kubernetes、Redis、消息中间件或微服务。
5. 不在计划书中保存任何本地或服务器账号、密码、API Key、JWT Secret、数据库 DSN 或对象存储凭证。


最终判断
--------

AIgo 当前最适合采用“强化单机 + PostgreSQL 持久队列 + 明确背压”的路线。先完成 P0 后，小服务器也能在超过容量时保持核心业务可用；完成 P1 后再做一次同规格压测，届时才能准确回答需要升级服务器、拆数据库，还是增加应用实例。任何横向扩展都必须等批量队列、文件存储、缓存失效和全局限额完成多实例改造后再进行。
